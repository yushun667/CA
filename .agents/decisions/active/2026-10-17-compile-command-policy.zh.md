# 决策：编译参数来源策略

Status: active
Date: 2026-10-17

## 背景

抽取精度取决于真实编译参数（include 路径、宏、目标 ABI、语言标准）。目标仓库使用 CMake、Meson、普通 make 或 Linux 内核构建系统，很多不提供 `compile_commands.json`。静默猜测参数会产生看似合理但错误的 AST，使精度无法评估。

## 决策

按以下顺序获取编译命令，并在每个 TU 记录来源：

1. 读取已有 `compile_commands.json`（文件或构建目录）；
2. 通过生成的编译器包装器（`CC`/`CXX` 拦截）俘获真实构建，记录原始 argv 与工作目录；
3. 从 Linux 内核构建树的 `*.cmd` 文件重建命令；
4. 仅当不存在任何真实来源时合成参数，且必须 `CompilationUnit.source == "synthesized"`。

来源写入数据库并通过 CLI 展示；合成命令绝不能被当作真实构建参数呈现。

## 原因

真实参数是 Clang 解析精度的最大杠杆。包装器适用于任何尊重 `CC`/`CXX` 的构建系统；显式导出可用时更快；内核格式常见到值得直接支持；显式声明降级路径让工具保持诚实，用户可过滤低置信结果。

## 考虑过的替代方案

- **强制要求编译数据库**：会排除大量从不导出的 OS 仓库。
- **总是合成参数**：易运行但精度低且误导。
- **只写各构建系统专用解析器**：脆弱且无穷无尽（autotools、kbuild、自定义脚本）；包装器可泛化。
- **依赖 `bear`**：macOS 未安装且仍要求构建成功；自研包装器让工具自包含。

## 后果

- 俘获构建要付出包装器开销并要求 configure/build 成功；失败时必须保留部分俘获并报告退出码。
- 内核 `.cmd` 规范化是内核专用的，必须去掉 `-o`/依赖噪声，保留 defines、include 与 `-include`。
- 合成 TU 精度较低，必须在所有位置标注。

## 验证与风险

用俘获的交叉编译器调用构建 xv6 并产出真实 `compile_commands.json`；合成来源有测试覆盖；数据库按 TU 记录 `source`。风险：绕过 `CC`/`CXX` 的构建系统；要检测并记录，不能静默降级。

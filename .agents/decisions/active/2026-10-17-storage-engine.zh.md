# 决策：存储引擎

Status: active
Date: 2026-10-17

## 背景

分析器需写入数十万至数百万条 AST/CFG/数据流记录，并快速回答符号、调用者/被调用者、分支与资源查询。它是单用户 CLI 工具，必须可移植且不需要服务器。数据库是系统记录，也供精度评估与基准使用。

## 决策

以 SQLite 为主引擎：WAL 日志模式、以稳定 TEXT ID 为主键的规范化表、显式事务中批量写入、在 `finalize()` 建索引后执行 `ANALYZE`。DuckDB 仅用于可选的分析实验与导出；阶段 1 不引入服务器数据库。

## 原因

SQLite 随 Python 提供、是单文件、易于移植，适合单写者 + 并发读者（与流水线一致：worker 产出结果，主进程写入），索引良好的点/范围查询可达微秒级。批量加载后建索引能保持写入速度。

## 考虑过的替代方案

- **DuckDB 作为主存储**：列式分析与批量加载优秀，但单写者、行级更新模式不成熟，作为点查询主库偏重；保留为可选分析路径而非系统记录。
- **PostgreSQL**：查询规划与并发强，但服务器运维与凭据超出本地 CLI 范围。
- **图数据库（Neo4j/Kuzu）**：适合调用图，但模式/写入复杂度与运维重量不被阶段 1 查询需求证明合理。
- **LMDB/RocksDB**：KV 很快，但缺少 SQL 与面向 CLI 的即席关系查询。

## 后果

- 有索引的查询快；大规模无索引分析扫描慢于列式引擎，阶段 2 如需以分析为主可加 DuckDB 导出。
- 流水线天然单写者；并发 CLI 读者使用 WAL。
- 数据库文件可移植，可用标准工具检查。

## 验证与风险

在至少 50 万函数、100 万调用的合成数据集上测批量写入吞吐与查询 p50/p95，并用 `EXPLAIN QUERY PLAN` 验证关键查询。风险：索引过多拖慢写入；要测量并只保留实际查询需要的索引。

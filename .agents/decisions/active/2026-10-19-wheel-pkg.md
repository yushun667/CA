# Decision: install CA from wheels with an offline wheelhouse

Status: active
Date: 2026-10-19

## Context

The plugin originally required users to provide an existing CA checkout and venv, or
rsync'd the checkout to a remote Linux host and installed it editable, because
`pyproject.toml` declared no package-data: a built wheel silently missed
`src/ca/store/schema.sql` and the UI static assets. That assumed Python tooling, PyPI
access, `rsync` and a writable source tree on every backend host — untrue for DSH
desktop users and for air-gapped servers. A new user should become productive without
a build step.

## Decision

- Make the Python package wheel-complete: declare package-data (`ca.store` schema and
  `ca.ui` static files), add `MANIFEST.in`, build
  `ca_analyzer-<version>-py3-none-any.whl` and bake it into the plugin at
  `dsh/backend/wheels/` (about 360 KB).
- Install the backend from that wheel by default, locally (Windows/macOS/Linux) and on
  remote Linux: create a private venv, `pip install` the wheel (online dependencies
  come from PyPI) and verify `ca version --json`. The old rsync + editable source flow
  remains only as `mode:'source'` / developer fallback.
- Add an offline path: `dsh/scripts/build-wheelhouse.mjs --platform <id>` builds a
  per-platform dependency wheelhouse (`linux-x64`/`arm64`, `macos-arm64`/`x64`,
  `windows-x64`, about 41–46 MB) in `artifacts/wheelhouse/<platform>/`; pip then runs
  with `--no-index --find-links`. Remote offline installs upload the wheelhouse over
  scp, or as a tar stream through ssh.
- Require Python >= 3.11 up front (probe `py -3.13/3.12/3.11` on Windows and
  `python3.13/3.12/3.11` elsewhere; fail fast with `UNSUPPORTED_PYTHON`).
- Persist the last successful install summary in `install-state.json` (0600) and expose
  it through `backend.get.install` and `backend.installStatus`; the backend page owns
  Install/Repair and the online/offline and wheel/source choices.

## Reasons

- A wheel plus wheelhouse makes installation deterministic, offline-capable and
  platform-explicit; nothing is compiled at install time.
- Baking the CA wheel into the plugin keeps the plugin and the analyzer package in
  sync and removes the registry dependency.
- Wheel-complete packaging also fixes any other wheel-based `ca serve`/`ca ui` install,
  not only this plugin.
- Python 3.11 is the declared project minimum; detecting it before pip gives an
  actionable error instead of a late pip failure.
- Keeping source mode limits risk: existing developer deployments and debugging flows
  keep working.

## Alternatives considered

- **Keep editable installs as the only path**: rejected — needs a checkout, toolchain
  and network on every host and fails on Windows/air-gapped servers.
- **Publish CA to PyPI and install from the index**: rejected — ties the plugin to a
  release process and registry availability and makes offline installs impossible.
- **Vendor a virtualenv/zipapp**: rejected — platform-specific and large; wheels are the
  standard, auditable artifact.
- **Ship one "all platforms" wheelhouse**: rejected — dependency wheels are
  platform-specific; the builder validates target pip tags.
- **Keep remote source/rsync as the default**: rejected — `rsync` and a writable
  checkout were the main remote-setup failure source.

## Consequences

- New installs use **Install / repair** on the backend page: online needs network only;
  offline needs a wheelhouse generated once for the target platform.
- The plugin carries a binary artifact (`dsh/backend/wheels/`) and `package.json`
  `files` includes `backend/**`, so plugin installs copy the wheel.
- Windows code paths are implemented but not verified on real hardware, and CA `watch`
  is unavailable on Windows; remote backends are Linux-only.
- Offline `.tar.gz` packs must be extracted before local `pip --find-links` use.
- Measured: macOS arm64 offline local install ~1.4 s; real Linux server offline wheel
  install ~6.4 s including a 46 MB wheelhouse upload.

## Validation and risks

Unit/contract tests cover platform ids, Python probing, install step machines, upload
strategy planning and install-state/status merging; real-machine checks cover macOS
arm64 and a Linux server. Risks: dependency wheels must match the target platform and
Python ABI; pip versions differ in wheelhouse generation; the baked wheel must stay in
sync with `pyproject.toml`; Windows paths remain unverified.
